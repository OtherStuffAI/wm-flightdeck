Design handoff for discussion, not an implementation dispatch. Requested by @[Pete’s request for separate component design threads](mention:message:349f1278-e8b2-4ed7-a7a9-6dea384d6705). @[Shared design, rationale and full acceptance criteria](mention:message:22cbecbd-d27f-4a22-ae04-6f941ebc709d).

**Outcome and scope**

Adding or editing a record should touch that record, required related records and the visible result window. Loading and navigation should remain responsive as stored history grows. Workdir: /Users/mini/code/wm/flightdeck. Preserve TowerSyncService → Dexie → liveQuery → UI and the existing workers. React, native UI and multi-vault work remain separate decisions.

**Confirmed starting points**

src/db.js: replacePgTasksForChannel() scans all tasks and replaces the channel set; replacePgMessagesForChannel() avoids unchanged writes but reads channel history. getMessagePresentationWindowByChannels() fetches whole histories before windowing. The existing [channel_id+updated_at] index already supports targeted reads elsewhere. src/pg-read-hydrator.js applies ordinary bundles using replacement helpers. Review src/section-live-queries.js for subscriptions that rerun broad queries.

**Implementation packages**

1. Baseline and inventory. Record each hot query’s filters, sort semantics, pagination, index, rows read and subscription scope. Benchmark fixed visible windows with 1k/10k/100k stored messages and large task/comment datasets. Measure payload, materialisation, query and UI costs separately.
2. Indexed local reconciliation. Add the missing task pg_channel_id index and an indexed optimistic-client-ID lookup where required. Batch-get incoming primary keys, compare server versions/canonical data and bulk-write only changed rows. Keep complete-snapshot reconciliation separate from partial updates. Preserve pending writes and reconcile acknowledgements exactly once. A capped response never authorises deletion by omission.
3. Bounded view queries. Use channel + timeline timestamp + record ID keyset queries; explicitly choose creation order versus updated activity order. Index thread/parent + chronology + ID for paged replies and target + chronology + ID for comments. Use bounded per-channel reads and a bounded merge for multi-channel feeds. Select task-board indexes from actual scope/channel + state + sort filters; query counts separately and paginate cards visibly. Avoid redundant indexes and measure write/storage cost.
4. Record-delta consumer. Add applyPgRecordChanges() behind negotiated protocol support. Each page applies upserts, explicit deletions, dependent summaries and next_cursor in one Dexie transaction. Ignore stale/replayed versions, retain unresolved local commands, and surface remote/local conflicts. Yield between bounded committed pages. Keep old-protocol support during rollout with distinct cursor compatibility rules.
5. Summaries and subscriptions. Maintain per-channel latest activity and viewer-specific unread/read-watermark summaries. Define unread semantics before coding. Use indexed predecessor lookup when deleting the latest item; provide bounded backfill/rebuild and equivalence checks. Subscribe views only to visible pages and small summaries. Cached data renders first; missing data is requested through TowerSyncService.

**Tower dependency / shared contract**

Proposed versioned response: protocol_version, mode, changes, next_cursor, has_more; snapshot_id and partition completion markers for snapshots. Changes identify family, ID, operation, version/order and ownership context, with full canonical upsert rows or explicit deletion identities. Tower owns final OpenAPI/fixtures, committed cursor ordering, permission-filtered records, grants/revocation instructions, byte/page bounds and snapshot handover. Do not infer completion from missing rows. Never switch record-delta mode before Tower support is detected.

**Validation and release**

First ship compatible local/index/query changes; they reduce local work but do not remove collection-sized payloads. Then integrate Tower contract fixtures and record deltas, followed by summary backfills. Test Dexie migration with old-schema tabs, cached data and pending writes. Retain recoverable cursors and pending commands on rollback.

Acceptance: one-message delta on a synced 100k-message channel causes no history scan or unrelated row rewrite; a fixed UI page uses bounded reads as history grows. Test same-timestamp pagination, huge threads, edits/deletes, optimistic ID replacement, duplicate/reordered pages, crash/replay, grant/revocation and snapshot races. Compare median/p95 on the same desktop/mobile targets; agree absolute budgets from baseline. Run focused tests and repository-required build/test checks once implementation is authorised.
